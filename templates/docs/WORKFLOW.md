# GitHub 개발 운영

기준 저장소: https://github.com/{{REPO}}
표준 원본: https://github.com/krdn/gon-github-workflow

## 시작

`gon-workflow start . --repo {{REPO}}`는 중앙 main을 갱신하고 원본 버전을 조회한다.
변경 후보가 있으면 중앙 저장소에서 `upgrade`, 영향 검토, 테스트, 독립 리뷰 기록(record-review), PR CI·merge를 먼저 완료한다.
인터넷 오류는 최신 확인 성공이 아니다. 오류를 해결한 뒤 다시 실행한다.

start가 Git 초기화, 원격 저장소, 첫 이슈·Milestone·Project 연결, 구성 커밋·푸시를 수행한다.
새 저장소는 기본 public이며 필요할 때 `--visibility private`을 지정할 수 있다. 기존 공개 범위는 보존한다.
`gon-workflow ready .`로 원격 커밋과 연결을 확인한다. URL은 `.github/project-setup.json`에 있다.

AI 조사·계획·구현은 구성 완료 후 이 프로젝트에서 별도로 요청한다.
그때 `docs/start-context.json`에 목표, 공식 출처와 확인 내용, 기술 선택, 실제 checked_at을 기록한다.
status를 reviewed로 바꾸고 `gon-workflow implementation-ready .`로 24시간 이내 조사 기록을 확인한다.
이 검사는 출처의 진실성·기술 호환성·AI 실행 성공을 증명하지 않는다.
첫 이슈의 목표를 구체화하고, 큰 작업은 하위 이슈와 의존 관계를 사용한다.
이슈에는 type:feature·type:bug·type:docs·type:research·type:maintenance 중 맞는 종류를 붙인다.
필요할 때 priority:high·status:blocked·needs:input·workflow:ai를 추가한다. 일반 진행 상태는 Project에서 관리한다.
새 공개 저장소의 main은 PR·configuration 검사·리뷰 대화 해결을 요구하며 강제 푸시·삭제를 차단한다.

## Claude·Codex 권한 설정

워크플로 최초 적용 때 없는 `.claude/settings.local.json`에 `permissions.defaultMode: bypassPermissions`, 없는 `.codex/config.toml`에 `approval_policy = "never"`와 `sandbox_mode = "danger-full-access"`를 생성한다.
기존 워크플로 프로젝트에 재적용하면 권한 파일을 추가하지 않는다. 기존 파일·사용자 수정·삭제는 보존한다.
Claude 로컬 파일은 게시 대상에서 제외하고 새 `.gitignore`에도 제외 규칙을 넣는다. 기존 `.gitignore`에 규칙이 없으면 직접 추가한다. 제외하지 않은 미추적 파일은 `handoff`를 중단시킨다.
새 Codex 파일은 seed로 게시하되 Git에서 무시한 파일은 로컬에 보존한다. 원래 있던 설정 파일은 게시 대상으로 등록하지 않는다.
[Claude 공식 설정](https://code.claude.com/docs/en/settings-reference#permissions-defaultmode)에 따르면 v2.1.257부터 프로젝트 파일의 `bypassPermissions`는 적용되지 않는다. 실제 실행에는 `claude --permission-mode bypassPermissions` 또는 사용자 설정이 필요하다.
Codex는 [신뢰한 프로젝트](https://learn.chatgpt.com/docs/config-file/config-basic)의 설정을 읽는다. 전역 설정·프로젝트 신뢰·실행 인자는 자동 변경하지 않는다. 파일 생성과 실제 권한 적용은 별도로 확인한다.

## GitHub 기록과 세션 시작

모든 계획된 설계·구현은 GitHub 이슈에 범위·완료 조건을 먼저 기록하고, 설계·작업 파일을 커밋·푸시해 원격 링크로 연결한다. 대화나 로컬 파일만을 작업 기준으로 삼지 않는다.
새 세션은 `gon-workflow resume <경로> --issue URL --task docs/tasks/N-task.md`로 원격 기록을 확인한다. 별도 설계는 `--plan`, 관련 PR은 `--pr`로 모두 지정한다. 같은 세션에서 계속할 때도 이슈·문서·검증 기록을 갱신한다.
필요한 추가 개선은 현재 목표와의 관계·완료 조건을 먼저 기록하고 범위 안에서 구현한다. 독립 기능은 후속 이슈로 분리한다. 이슈 등록은 거래·배포·삭제 등 별도 실행 승인을 뜻하지 않는다.

단순 질의에는 이슈를 만들지 않는다. 작은 변경은 기존 이슈의 체크리스트와 짧은 작업 기록을 재사용한다. 설계 PR은 후속 구현 이슈를 자동 종료하지 않는다.

```bash
gon-workflow resume . --issue https://github.com/{{REPO}}/issues/N \
  --task docs/tasks/N-task.md --plan docs/plans/feature.md \
  --pr https://github.com/{{REPO}}/pull/P
```

`--plan`·`--pr`은 반복 가능하다. 별도 설계가 없으면 작업 파일에 계획을 기록한다. 이슈와 작업 파일의 정확한 이슈 URL, STATE·작업·지정 설계의 로컬/커밋/원격 일치, native 선행 관계, 지정 PR/CI를 확인한다. 새 세션을 실제 생성하지 않는다. JSON의 미지정·빈 CI·실패를 성공으로 해석하지 않는다.

명령 성공은 기록 확인이다. 선행 이슈의 not_planned 종료·열린 상태, PR 미통합·head 불일치, CI 실패/대기, 사용자 승인·소유권을 판단한 뒤 해당 범위의 다음 행동을 정한다. CI 실패 수정은 같은 이슈로 진행할 수 있다. 문서의 충분성이나 지정하지 않은 PR까지 검사하지 않는다.

미커밋·미푸시·원격 불일치·조회 실패이면 자동 stash/삭제/재초기화하지 않는다. 소유권을 확인하고 변경을 보존한 뒤 기록을 갱신한다. clean 체크아웃에서 확인하는 경우 작업 중인 다른 worktree의 미커밋 변경은 별도로 보고한다. 검증 시각 이후의 변경도 착수 전에 확인한다.

## 작업

1. 이슈: 목표·수용 기준·범위·검증 방법을 기록한다.
2. 큰 기능: `docs/`에 명세와 계획을 쓰고 이슈에서 연결한다.
3. 버그: 재현 → 원인 → 수정 → 원래 증상 재검증을 구분한다.
4. 작업 브랜치와 PR에서 구현하고 CI·필요한 리뷰를 확인한다.
5. 배포: 프로젝트의 실제 Actions·Environment·Release 경로를 사용한다.
6. 마무리: 변경 SHA, 검사 결과, 이슈/PR/배포 링크와 다음 행동을 요약한다.

작은 수정에 전체 명세 절차를 강제하지 않는다. 앱 검증·배포 명령은 실제 스택에 맞게 구성한다.
동작하지 않은 배포 workflow나 빈 성공 job을 완료 증거로 삼지 않는다.

## 세션별 작업과 재개

큰 요청은 검증·전달이 가능한 작업으로 나누고, 작업별 완료 조건과 선행 의존관계를 이슈에 기록한다.
착수할 작업의 [양식](tasks/TEMPLATE.md)을 복사해 `docs/tasks/<이슈번호>-<짧은이름>.md`를 만든다.
동등한 작업 기록이 이미 있으면 재사용한다. 사소한 수정은 STATE의 짧은 기록만으로 충분하다.
구성만 요청받은 start 단계에서는 실제 개발 작업·사용자 결정을 만들어내지 않는다.

큰 작업을 분할할 때 다음 기준을 적용한다.

- 기존 구현·검증과 남은 변경을 분리한다. 이미 동작하는 기능을 신규 구현으로 계산하지 않는다.
- 사용자가 확인할 결과별 이슈와 공통 서비스 이슈를 나누고, 각 동작의 구현·수용 책임을 한 곳에 지정한다. 후속 이관 항목에는 받는 이슈를 연결한다.
- 기존 미통합 PR이 있으면 후속 구현의 기준 브랜치·SHA와 통합 조건부터 정한다. 완료·수용·merge가 확인되지 않은 기준선을 완료로 가정하지 않는다.
- native 하위 이슈와 blocked-by를 등록·재조회하고 누락·중복·순환을 확인한다. 지원되지 않으면 본문 링크로 대체하고 native 미적용을 표시한다.
- 선행 조건은 이슈 종료·검증·통합·사용자 수용 중 무엇이 필요한지 명시한다. not_planned 종료는 의존 기능이 완성됐다는 증거가 아니다.
- 이슈별 변경 수용과 최종 통합 수용의 대상을 나눈다. fixture·조회·실제 동작의 증거도 구분한다. 외부 계약은 다수 후속 작업의 전제가 되기 전에 최소 검증한다.
- 현재 명세와 다음 변경 목표를 구분하고, 구현 PR에서 관련 명세도 갱신한다. 변동하는 진행 상태는 GitHub에 유지한다.
- Project의 기존 상태·필드를 재사용한다. 착수 가능·진행·검토·차단·완료의 의미를 정하고, 의존성 해제와 상태 전환이 자동이라고 가정하지 않는다.
- 파일 소유권이 겹치면 순차 실행한다. 한 세션은 선택 이슈 하나에 집중하며, 세션 종료가 그 이슈 완료를 뜻하지 않는다.

`docs/STATE.md`는 목표·공통 결정·현재 작업 파일·다음 작업·차단 사유를 안내하는 목차다.
약 2,000자를 목표로 하고 12,000자를 넘기지 않는다. 완료 이력과 상세 근거는 작업 파일·이슈·PR로 연결한다.
작업 파일은 범위·완료 조건·필수 읽기 목록·브랜치/SHA·검증/미검증·실패·다음 행동을 짧게 유지한다.
로그·대화·전체 코드 복사를 피하고, 필요한 파일의 절·심볼과 검증 결과 링크를 남긴다.

새 세션은 다음 순서로 재개한다.

1. 적용되는 AGENTS와 STATE를 읽고 사용자가 지정한 작업 또는 STATE의 현재 작업을 고른다.
2. 그 작업 파일과 필수 읽기 목록만 먼저 읽는다. 지난 작업 파일·전체 이슈 목록·과거 대화를 일괄 읽지 않는다.
3. 현재 브랜치·미커밋 변경·관련 이슈·PR·CI를 조회해 기록된 SHA와 대조한다. 차이가 있는 부분만 추가 확인한다.
4. 확인한 미완료 행동부터 진행한다. 요약만으로 검증 성공·승인·소유권 이전을 추정하지 않는다.

작업 완료, 검증/리뷰 차단, 다른 작업으로 전환할 때 기록을 갱신한다.
재개 가능한 코드·작업 파일·STATE를 커밋·푸시하고 원격 SHA를 확인한다. 미완성 작업은 초안 PR로 전달한다.
커밋하지 못한 변경이 있으면 파일·보존 위치와 원인을 명시하고 다른 환경에서 재개 가능하다고 표시하지 않는다.
`gon-workflow handoff . --issue https://github.com/{{REPO}}/issues/N --task docs/tasks/N-task.md`로 선택 작업을 전달한다.
`--task`는 선택 항목이다. `--dry-run`은 같은 원격 검사를 거쳐 게시할 문구만 출력한다.
명령은 clean 작업 트리·origin·현재 브랜치의 원격 SHA·전달 파일을 확인한 뒤 커밋 고정 링크를 게시하고 댓글 본문·대상을 재조회한다.
같은 전달의 순차 재실행은 기존 댓글을 재사용한다. CI·사용자 수용·제품 동작은 이 검사와 별도로 확인한다.
마지막에는 현재 상태·남은 행동·새 세션 시작 문구만 짧게 전달한다. 세션 전환 자체가 작업 완료는 아니다.

새 세션 시작 문구: “docs/STATE.md의 현재 작업 파일과 필수 읽기 목록, 관련 이슈·PR·CI만 먼저 확인하고 다음 행동부터 이어가줘.”
현재 작업의 디버깅이 이어지면 같은 세션을 사용한다. 작업 경계가 분명하고 인수인계가 검증됐으면 필요한 기록만 읽는 새 대화를 권한다.
누적 토큰 사용량과 현재 컨텍스트 잔여량을 구분한다. 특정 용량 임계값이나 새 세션의 성능 향상을 가정하지 않는다.
새 탭·기존 세션 resume·대화 fork는 독립된 새 대화 시작과 다르다. `handoff`는 전달문을 만들며 세션을 실행하지 않는다.
사용자가 새 세션 실행을 요청했다면 현재 도구 지원을 확인하고 수행한다. 새 세션 ID·프로젝트 경로·첫 작업을 확인하며, 탭 가시성까지 요청받으면 화면도 확인한다.
세션 기능이 없으면 미실행 사실과 준비한 시작 문구를 보고한다. 이미 허용된 실행 범위를 반복 승인받지 않으며 사용자 수용·추가 권한은 만들어내지 않는다.
현재 세션에서 계속해야 해도 같은 작업 분할·선택적 읽기 규칙을 적용한다.

## 업데이트와 복구

다음 신규 시작 또는 명시적인 표준 갱신 때 `start`를 다시 실행한다.
사용자가 수정한 관리 파일이 있으면 전체 적용을 중단한다. diff를 검토해 별도 PR에서 통합한다.
`workflow-state.json`의 해시만 고쳐 충돌을 숨기지 않는다.
이전 버전 복구는 적용 PR을 revert하고 해당 중앙 revision과 lock을 함께 복구한다.
오래된 원본을 사용하는 예외는 근거와 만료 조건을 이슈에 기록하며, 최신 확인으로 표시하지 않는다.

## 협업과 GitHub 기능

Buzz 에이전트: `ggw-<project>-<role>`, 채널: `ggw-<project>-<topic>`.
역할: coordinator, researcher, implementer, reviewer. 동일 파일 소유권을 겹치지 않는다.
설계 탐색은 Discussions, 확정 결정은 docs, 실행은 Issues, 상태는 Projects, 통합은 PR로 연결한다.
Buzz 응답은 이슈로 옮기고 생성 초안과 실제 저장·응답 확인을 구분한다.
Packages·Pages·배포는 제품에 해당할 때 구성하고, 미적용 사유는 `.github/project-management.md`에 남긴다.
